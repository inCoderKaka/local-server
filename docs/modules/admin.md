# admin module

## Purpose

The admin UI's API handlers: the admin API at `/admin/v1` and `/metrics`, served on the admin listener only. Writes go through the owning modules; every write is audited in the same unit of work as the change.

## Owns

- Packages: `internal/admin/` (built by PLT-F-024) and `internal/admin/consumers/` (PLT-F-025), the logic behind the consumer, access key and invite operations, and `internal/admin/grants/` (PLT-F-026), the logic behind the grant, model and policy rule operations. Package admin only maps the generated types onto them and their errors onto the envelope.
- Tables: none (it uses `idn_*` through `internal/identity`, `aud_event` through `internal/audit`).
- Port: none defined here. It takes narrow interfaces for the sharing state, the host-metrics sampler, the host keys (host kid) and the model engine.
- Config: besides the sharing state, sampler, host keys, engine and metrics handler, `admin.New` takes `Grants` (`*grants.Repos`, to name models and check a key's narrowing against the grant), `Auth` (`*auth.Service`, narrowed to `consumers.Auth`: `Issue`, `Revoke`, `Invalidate`) and `Events` (the events `Notifier`, which runs every consumer, key and invite write). All three are required, and `Auth` and the config share one clock.
- Handler: `admin.New(Config)` then `Handler()`. The handler is the request id middleware, then the credential guard of `internal/auth/credential` (the Host check against DNS rebinding, the Origin check against CSRF), then a router: `GET /metrics`, `/admin/v1/...`, and a 404 in the error envelope for everything else, including every consumer route. The admin routes are not on the consumer listener, and the consumer routes are not on the admin listener.
- Routes implemented by PLT-F-024: `GET` and `POST /admin/v1/setup` (first-run admin; exactly one), `GET`, `POST` and `DELETE /admin/v1/session` (current admin, login, logout), `GET /admin/v1/host`, `POST /admin/v1/host/pause`, `POST /admin/v1/host/resume`, `GET /admin/v1/host-metrics`, `GET /admin/v1/host-metrics/history`, `GET` and `PATCH /admin/v1/settings`, `GET /admin/v1/audit-events`, and `GET /admin/v1/usage` (the usage module's query function, served a second time, req_001 D-104). PLT-F-025 adds `GET` and `POST /admin/v1/consumers`, `GET`, `PATCH` and `DELETE /admin/v1/consumers/{consumer_id}`, `POST .../suspend` and `.../reactivate`, `GET` and `POST /admin/v1/consumers/{consumer_id}/access-keys`, `PATCH /admin/v1/access-keys/{access_key_id}`, `POST .../revoke`, `GET` and `POST /admin/v1/invites` and `POST /admin/v1/invites/{invite_id}/revoke`. PLT-F-026 adds `GET` and `PUT /admin/v1/consumers/{consumer_id}/grant`, `GET .../grant/versions`, `GET /admin/v1/models`, `PATCH /admin/v1/models/{model_id}`, `GET` and `POST /admin/v1/policy-rules`, `GET`, `PUT` and `DELETE /admin/v1/policy-rules/{policy_rule_id}` and `GET .../versions`. Every other admin operation answers `501` in the error envelope once the caller is logged in.
- Consumers, keys and invites (PLT-F-025, `internal/admin/consumers/`):
  - Every write is one unit of work run by the events Notifier's `Write`, with its audit rows; the actor is the logged-in admin. After the unit commits, suspend, reactivate, delete and a key update call `Auth.Invalidate()`, because the auth cache clears itself only on `access_key.revoked` and `grant.changed`. Revoke relies on the `access_key.revoked` event `auth.Service.Revoke` emits.
  - Create makes a key-only consumer (a principal of kind `consumer` and its consumer row; no grant, which `PUT .../grant` creates). Update changes the display name, email or billing mode (`none`, `prepaid` or `postpaid`, set by the host admin only, never null; a consumer created without one has `none`, req_001 D-107); a deleted consumer is refused with 409, and a change that alters nothing writes nothing. Suspend and reactivate are idempotent (no audit row when nothing changes); a deleted consumer is never reactivated or suspended (409, req_001 D-54).
  - Delete (req_001 D-40) revokes every key that is not revoked through `auth.Service.Revoke`, erases the display name and email, the key names, the login credentials (the rows are removed) and the notes of invites the consumer redeemed, revokes the sessions, and sets the principal to `deleted`. The consumer row, the key rows, the invite rows, the usage records and the ledger leaves stay. Consent records (`idn_consent`) stay untouched, including their `evidence` column: they hold a purpose, a policy version, times and that evidence, and are the record that terms were accepted. Whether delete should erase `evidence` is an open ruling (I-323). Delete does not reach the consumer-directory change rows (`syn_change`) written before it: they still hold the earlier display name and email until the `sync.change.retention` rule prunes them. Deleting twice is a no-op.
  - Issue returns the whole key once (`telemetry.Redacted` in the service, revealed only by the handler that writes the 201 answer); the list and every other answer show the prefix. A key is `active`, `expired` (its expiry passed) or `revoked`. An update of a revoked or expired key is 409; a past expiry is 400 (to end a key now, revoke it); revoking a revoked key is a no-op.
  - A narrowing is given with model names and stored with model ids. A model must exist on the host. When the consumer has a current grant version, a model the grant lacks, or a number above the grant's own (a quota entry above the grant's entry of the same metric and window, concurrency, or a context or output limit above the largest cap when every model of the grant has one) is refused with 400 and param `narrowing.<field>`; entries of a window the grant has no entry for are not compared and both are enforced. A quota entry is checked for a known metric, a limit of at least 0, a whole-second window within `limits.quota_window_min` and `limits.quota_window_max`, and no repeat of a metric and window (400, param `narrowing.quotas.<index>.<field>`). The deprecated `narrowing.quota` object is expanded to entries with the window `limits.quota_window`; when `narrowing.quotas` is also given the list wins and the answer's `warnings` says so (it is filled by issue and update only). Only a consumer with a billing mode other than `none` may set windows on its own keys: when the actor is the consumer's own principal and the consumer is `none`, quota entries are refused with 403 (`consumers.MaySetQuotaWindows`; no consumer self-service route exists yet, the host admin always passes). A consumer without a grant yet gets only the checks that need none. A narrowing given in a PATCH replaces the stored one whole.
  - An invite stores a prefix and a hash of its token. Without `expires_at` it lasts `invites.ttl` from the moment it is created. The token and the link `invites.link_base_url + /invite#<token>` (relative `/invite#<token>` when the base is empty) are in the 201 answer only. Its state is derived: `redeemed`, `revoked`, `expired` or `pending`. Revoking an invite that is not pending is 409.
  - Lists are newest first, paged by an opaque cursor (the creation time and id of the last row), with `admin.list_page_size` as the default and the cap; a limit below 1 and a malformed cursor are 400 (params `limit`, `cursor`); on the consumer list an unknown status is also 400 (param `status`). A deleted consumer is listed only with `status=deleted`.
  - Audit rows from these operations never hold a display name, an email, a key name, an invite note, a key or a token. Their detail keys are listed per action under Audit actions below.
- Grants, models and policy rules (PLT-F-026, `internal/admin/grants/`):
  - `PUT /consumers/{id}/grant` always makes a new immutable grant version and makes it current, even when nothing changed (req_001 D-25). It creates the consumer's grant row first when there is none. The version (with its windowed quota entries), the audit row `grant.changed` and the `grant.changed` event are one unit of work run by the events Notifier's `Write`; after the commit the service calls `Auth.Invalidate()` (the auth service also clears its cache when it receives the event). A consumer that does not exist is 404; a deleted one is 409. `GET .../grant` is the current version (404 when the consumer or its grant is missing) and `GET .../grant/versions` lists them newest first, paged like the consumer list (opaque cursor, `admin.list_page_size`); `resource_request_id` is always null until resource requests exist.
  - A grant is checked before anything is written; each refusal is 400 with the request field as `param` (`limits.<field>`). `quotas` entries use `grants.ValidateQuotas` and the host's `limits.quota_window_min` and `limits.quota_window_max` (`limits.quotas.<index>.<field>`, the window as `window_seconds`); the deprecated `quota` is expanded with the window `limits.quota_window`, and when `quotas` is also given `quotas` wins and the answer carries `warnings`. `concurrency` and the per-model `context_limit` and `max_output_tokens` are at least 1, `on_context_overflow` is `refuse` or `truncate`, `expires_at` must be in the future, and a model name appears once. A model is named as the engine names it and must exist in `grt_model`; a name the host has not stored is looked for in the engine once. A model that is unknown, retired or not `allowed` is refused (`limits.models.<index>.model`). `allowed_request_properties` is required and nullable: `null` allows any request property and `[]` none. A grant that sets no concurrency shows the host's `scheduler.default_grant_concurrency`; a model cap that is empty in storage shows as 0.
  - `GET /models` lists the engine's models (storing a `grt_model` row for each new one, closed unless `admin.model_default_allowed` is on) with `allowed`, `preload` (the name is in `scheduler.preload_models`), `keep_alive_seconds`, `loaded` and `size_bytes` (the loaded size, else the installed size). When the engine cannot be asked, the stored models are listed, none loaded. `engine` is `ollama` unless the engine has a `Name() string` method. `PATCH /models/{model_id}` changes `allowed`, `keep_alive_seconds` (null returns it to the host default) and `preload` (the service rewrites the setting `scheduler.preload_models` in the same unit of work as the audit row and the model row; the scheduler applies it when it changes, req_001 D-22). Closing a model does not edit the grant versions that hold it; only new grants are refused. A model that does not exist or is retired is 404. The per-model keep-alive is stored and shown, but the scheduler still uses `scheduler.keep_alive`.
  - A policy rule is immutable versions (req_001 D-87; storage in `docs/modules/grants.md`). `POST /policy-rules` and `PUT /policy-rules/{id}` check the document with `policy.ValidateRule(body, policy.rule.max_bytes)` and store the format version it returns, never one the caller gives; a refusal is 400 with the param `rule` (or `rule.format_version` for a version this host does not know) and fixed text that quotes nothing of the document. A name is 1 to 120 characters (default: the rule's id), a position is 0 or more (default 0). `grant_id`, when given, must be an existing grant (400, param `grant_id`). `PUT` stores a new version when the name, order or document differ, and `enabled` in the body switches the rule without making a version; fields left out keep their value. `DELETE` is a soft delete (204): the rule stops applying at once and a second delete is 404. `GET /policy-rules` lists every rule that is not deleted, or with `grant_id` only that grant's own rules, in evaluation order; `GET .../versions` lists the history newest first (only the live version carries `enabled`). A deleted rule is 404 everywhere.
  - Auto-disable (req_001 D-73, PLT-B-020): the gateway counts failed evaluations of a rule that does not parse (`RuleFailures`) and raises `policy.rule_invalid`. `Service.DisableFailingRules` switches off, in storage, every enabled rule without a `deny` field whose count reached `policy.rule.max_failures`, writes the audit row `policy_rule.auto_disabled` (the system as actor; rule id, failure count and limit only) in the same unit of work and then clears the count; a rule with `deny` is never switched off, and a document that cannot be read as an object counts as having none. `Admin.RunRuleSweeper` runs it every `policy.rule.check_interval`; `cmd/local-server` starts it as the `policy-rule-sweeper` worker and passes the gateway as `Config.RuleFailures` (an interface, because the admin module does not import the gateway; nil turns the sweep off). Replacing a rule whose document changed or which is switched off, and deleting a rule, call `ClearRuleFailures`. The host admin learns of a switched-off rule from the `policy.rule_invalid` event and the audit row; there is no separate event type.
- Sessions: the cookie `ls_admin_session` (HttpOnly, Secure, SameSite=Strict, Path `/`) holds a random token; `idn_session.token_hash` holds its hash. A session is valid while it is not revoked, not expired (`admin.session_ttl`) and its principal is an active `host_admin`. `admin.SessionOf` and `admin.PrincipalIDOf` give a handler the logged-in admin.
- `admin.Authenticator` (`Authenticate(ctx, username, password, remoteAddr)`): the one password check, with the login lockout; the HTTP login and the `recovery-code` command both use it.
- Command `local-server recovery-code [--data-dir DIR]` (in `cmd/local-server`): shows the recovery code again after an admin login, on a terminal only, and only after its audit row has committed (req_001 D-80, D-101).
- Settings (host-owned, req_001 D-38, D-54): `admin.max_body_bytes` (1048576), `admin.session_ttl` (12h), `admin.engine_probe_timeout` (2s), `admin.metrics_history_default_range` (1h), `admin.metrics_history_max_points` (1440), `admin.tailnet_name` (empty; the extra Host name the guard accepts, read per request). PLT-F-025 registers `admin.list_page_size` (50; the page size of the consumer and invite lists and its cap), `invites.ttl` (24h; the lifetime of an invite without `expires_at`) and `invites.link_base_url` (empty; an absolute http or https address without user information, query or fragment, put in front of `/invite#<token>`). PLT-F-026 registers `policy.rule.max_failures` (5; at least 1), `policy.rule.check_interval` (30s; greater than 0) and `admin.model_default_allowed` (false), and reads `scheduler.default_grant_concurrency`, `scheduler.preload_models`, `policy.rule.max_bytes` and the `limits.quota_window*` settings, registering their definitions too (an identical registration is allowed). All are host-owned and read per request. The password and login lockout settings are the auth module's (`auth.password.*`, `auth.login_lockout.*`).
- Audit actions: `admin.created`, `admin.session_started`, `admin.session_ended`, `setting.changed` (detail: key, old value, new value), `host.recovery_code_shown`; `consumer.created` (detail: consumer id, kind, billing mode), `consumer.updated` (detail: consumer id, field names), `consumer.suspended`, `consumer.reactivated` (detail: consumer id, from, to), `consumer.deleted` (detail: consumer id, count of keys revoked; target: the consumer's principal), `access_key.updated` (detail: key id, consumer id, field names), `invite.created` (detail: invite id, prefix, expiry) and `invite.revoked`; `grant.changed` (detail: consumer id, grant id, version number; target: the consumer's principal), `model.updated` (detail: model id and name, names of the changed fields), `policy_rule.created` (detail: rule id, grant id, version), `policy_rule.updated` (detail: rule id, version, enabled), `policy_rule.deleted` (detail: rule id) and `policy_rule.auto_disabled` (detail: rule id, failures, max failures; no actor); `access_key.issued` (detail: key id, prefix, consumer id, and when set the bound node, expiry and narrowing) and `access_key.revoked` (detail: key id, consumer id) are written by the auth module's `Issue` and `Revoke`, which the consumers service calls. `host.paused` and `host.resumed` are written by the host module with the admin as the actor. Failed logins and lockout triggers are not audited yet (PLT-F-055, req_001 D-89).

## Imports

Allowed and forbidden imports are enforced by `tools/archcheck` (`go run ./tools/archcheck`): no import cycles between modules, adapters imported only from `cmd/`, drivers only in their owning module. Core modules import ports, never adapters. The admin module imports `internal/api` (the generated server), `internal/auth` (the service, for `Issue`, `Revoke` and `Invalidate`, and `ParseNarrowing`), `internal/auth/credential`, `internal/identity`, `internal/grants` (read only, and the writes of `internal/admin/grants`), `internal/policy` (`ValidateRule`, `LoadLimits`) and `internal/scheduler` (the keys of two settings), `internal/notifier/events` (the `Notifier` port), `internal/audit`, `internal/host`, `internal/hostmetrics`, `internal/settings`, `internal/usage`, `internal/engine` (the port) and `internal/telemetry`. It does not import the gateway.
