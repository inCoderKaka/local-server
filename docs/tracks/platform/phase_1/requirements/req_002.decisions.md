## Open

| ID | Date | Question | Status |
|---|---|---|---|
| Q-01 | 2026-11-20 | Where does the portal's server run when it calls this host? `req_002.md` "use the current machine as a host for some AI actions" with D-02 (server-side route) against F-05 (Vercel). Options: (a) only when the portal runs on this machine or another tailnet machine (`next dev` / `next start`); (b) the Vercel deployment joins the tailnet (Tailscale in the function, an ephemeral auth key); (c) the browser talks to a small local relay on the user's own machine; (d) public mode (Funnel, phase 2 PLT-F-039) for hosted callers. | open |
| Q-02 | 2026-11-20 | Which tunable parameters are in scope? `req_002.md` "more tunable parameter in the client request" and "a lot of tunable parameters for various different functionalities". Options: (a) the portal's `GenParams` set (F-04) that Ollama can carry; (b) that plus Ollama-only options the portal does not use yet (`min_p`, `repeat_penalty`, `num_ctx`, `keep_alive`, `mirostat`); (c) every option the Ollama API exposes. | open |
| Q-03 | 2026-11-20 | Standard OpenAI fields that the engine could carry but local-server rejects today (F-02): should `frequency_penalty`, `presence_penalty`, `response_format` (`json_object` and `json_schema`) and `reasoning_effort` be accepted as standard body fields, beside the namespaced object for non-OpenAI options (D-02)? The portal's `extract`, `question.generate` and `scorecard` tasks need JSON output. | open |
| Q-04 | 2026-11-20 | What makes the integration "standard and consistent"? `req_002.md` last sentence. Options: (a) a capability-discovery answer (per model and caller: which options are supported, their ranges, the grant's caps), so PA and the portal stop hard-coding capability tables (F-03); (b) one documented contract in the developer guide only; (c) (a) plus a small shared client library for TypeScript. | open |
| Q-05 | 2026-11-20 | Can the host cap or forbid options per grant (for example a largest context size, thinking off, a highest `max_tokens`), beyond today's context and output limits? Options: (a) caps for options that cost host resources (context size, thinking, output length); (b) every option can be capped or forbidden; (c) no new caps, the host's model defaults only. | open |
| Q-06 | 2026-11-20 | Should a client name the task behind each call (for example the portal's `code.review`, `hint`, `scorecard`) so the host sees usage per task? Options: (a) a standard key in `LS-Request-Properties` (req_001 D-33) shown in usage; (b) no task attribution. | open |
| Q-07 | 2026-11-20 | Which portal AI tasks may run on this host ("some AI actions")? Options: (a) any text task the learner points at `local` (the portal's per-task profiles already choose a provider); (b) a fixed subset such as `code.review`, `hint`, `stage.grade`, `recall.grade`, `twists`; (c) text and vision tasks, not realtime voice. This decides which options and models the design must carry. | open |
| Q-08 | 2026-11-20 | Who changes the portal? req_001 D-04 lets this repo write only personal-assistant's requirement file, never its code. Options: (a) the same rule for the portal: this repo keeps a requirement file in the portal repo, the portal's own chats build it; (b) this repo may change the portal's code for the integration; (c) the portal's changes are designed and built in the portal repo only, from the developer guide. | open |
| Q-09 | 2026-11-20 | Does personal-assistant move to the same contract in the same release? `req_002.md` "like along with the personal assistant". Options: (a) yes, PA's requirement file is updated with the new options and discovery (req_001 D-145 pattern); (b) PA keeps today's contract and adopts the new one later. | open |
