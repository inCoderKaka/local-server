1. What I think you're asking for

A small app that runs on a host machine (to start with, your friend's Mac mini). It sits in front of a local model runtime and gives other people and apps authenticated, encrypted, metered access to AI models on that machine. The host gets an admin UI to:

- issue keys
- watch usage
- approve or reject requests for more resources

3. What's possible, what's not, and what I'd recommend

Feasible as written:
- Choosing allowed models, preloading or unloading them, keeping them in memory
- Context-length cap per model and per key
- Max output tokens, concurrency, rate limits and token quotas per key
- Usage per request, rolled up over time
- Showing "used by other apps vs. reserved for sharing" on every page
- Keys that can be created, revoked and set to expire
- The request, approve/reject and comment flow

Not truly enforceable on macOS:
- Hard caps on RAM, CPU or GPU. macOS has no cgroups, and Apple Silicon's unified memory can't be partitioned per process. I can enforce the share budget indirectly instead:
  - Refuse to load a model if its weights plus context-cache estimate exceed th
  - Cap concurrency and queue length
  - Lower the app's CPU priority

  It would be reported as a budget, not a hard wall. On Linux, real hard caps a
- GPU utilisation on Apple Silicon. Reading it needs sudo powermetrics. Memory and CPU are easy to read; GPU would be optional or best-effort.

ME: ignore the not truly enforceable things for now. Make it such that it is OS agnostic. It should be installable easily either through brew, winget or through simple git clone and adding to PATH etc. Ask me more questions to confirm all things around this.

Biggest hidden problem: reachability. The Mac mini sits behind a home router, and PA in production is on Fly. Something has to connect them. Options:
- (a) Tailscale. WireGuard, encrypted end-to-end, free tier, works with Fly.
- (b) Cloudflare Tunnel. Free, gives a public HTTPS URL. But Cloudflare decrypts traffic at its edge, so prompts are visible to them.
- (c) Port forwarding plus a certificate. Fragile, and it exposes the friend's
- (d) Our own relay server. Heavy, and an extra service to run.

→ Recommendation: put the transport behind an adapter. Default to Tailscale for "very secure"; offer Cloudflare Tunnel as the easy option for consumers who aren't on Tailscale.

ME: go with the recommendation except the fact that we need no compromise in the security... so Cloudfare should be ruled out, if there isn't anyway we can secure the cloudfare ourselves. Build for possible future own relay server.

Recommended building blocks:
- Don't write our own inference. Wrap an engine through an adapter. Ollama is taks it); MLX or llama.cpp later.
- Lightweight: a single Go binary, with SQLite for storage and the admin web UI built into the binary and served only on localhost. No Electron. The admin UI is never reachable from
  outside; only the consumer API is.
- Make it usable by "any application": expose an OpenAI-compatible API (/v1/chat/completions, /v1/embeddings, /v1/models) plus a /v1/capabilities endpoint that reports context limits.

  - Consumers can only run inference, never arbitrary code

- A public marketplace where anyone can find any host. It needs a central serving and legal terms.
